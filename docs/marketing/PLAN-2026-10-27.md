# JustSVG 营销方案：通过技术图案例建立开源影响力

制定日期：2026-10-27；更新日期：2026-10-28，补充产品发布社区与导航投稿。状态：方案待讨论；尚未启动营销、发布、评论或联系他人。D1 指后续明确开始执行的第一天，不代表今天已经开始。

用户已明确：目前没有社交媒体资源；希望同时建立个人 IP；中英文同等投入；首阶段优先 GitHub 关注与开源传播。以下工作量和目标是实验设计，不是增长预测。

## 1. 核心决策

用 JustSVG 持续把真实项目和复杂系统画清楚，让案例带动开源传播。AI 需求发现、定向评论和资源账号投稿承担分发；可复用的作品、方法和产品事实承担信任。

推荐的循环：

真实问题或公开项目 → 生成并检查技术图 → 展示编辑与改进过程 → 发布图稿、Prompt 和依据 → 相关用户复用 → 获得反馈和自发分享 → 改进下一份案例。

首月精力分配：案例和内容 40%，需求发现与定向参与 20%，产品发布与导航投稿 15%，资源策展投稿 15%，数据与复盘 10%。每一类工作尽量中英文各半；按制作、研究和分发时间核算，不强求两边曝光量相等。

首月默认不投广告、不买推荐、不买名单；以现有工具和免费渠道验证。运行工具、托管与可能的数据访问费用另列，不把它们假定为零。付费服务不作为首轮依赖。

## 2. 产品事实与对外定位

依据本地 README、PRODUCT、品牌说明和 Skill README：

- JustSVG 为 MIT 开源、SVG 原生的技术图创建与编辑工具，当前版本为 1.0.0-beta.1。
- 支持架构图、流程图、信息图，具有风格示例、模板、原生文字/图形编辑及 SVG 导出。
- 提供可独立分发的 SVG Diagram Skill；生成任务在支持该 Skill 的 AI 代理中执行，网页本身不调用模型。
- 编辑器本地优先，无账号或后端、无遥测。没有 `.drawio` 工程导入、整图自动布局、云端协作，也不应称为完整 draw.io 平替。
- 品牌研究是原创适配，不能宣传为 OpenAI、Figma 等公司的官方模板或合作。
- 本次未确认公网演示地址、仓库公开可访问状态、既有 Star/关注基线。README 中的 GitHub 地址是待验收入口，不能据此声称产品已公开上线。

建议中文主张：**用 AI 辅助生成技术图，直接编辑原生 SVG。图稿、Prompt 与工具一起开源。**

建议英文主张：**Create technical diagrams with an AI skill. Refine native SVG. Keep the source.**

长期品牌口号沿用“把复杂系统，画清楚 / Just diagrams. Just SVG.”。这只是营销表达聚焦，不改变产品已确定的范围。

“可编辑 AI 图”本身不足以证明差异：Excalidraw 官方已有可编辑 AI 技术图叙事，SVGEdit AI 也直接宣传 AI 生成后的 SVG 修改。因此要展示具体工作流、实际可用图稿、生成与人工编辑的衔接，以及事实检查，而不声称独家功能或未经测试的效率优势。[Excalidraw 官方产品页](https://plus.excalidraw.com/ai)、[SVGEdit AI 产品页](https://svgeditai.com/)（2026-10-27 查阅；均为厂商陈述，未做实测排名）。

> 我在做 JustSVG：用 AI 和原生 SVG，把复杂系统画清楚。持续公开技术图、Prompt 和踩坑记录。

> Building JustSVG. Sharing editable technical diagrams, prompts, and what breaks along the way.

个人 GitHub 主页、项目 README、案例署名与社交主页相互连接。产品账号不是首月重点；以作者个人身份持续回应具体问题，积累可被记住的判断和作品。

内容配比建议：60% 可复用案例，25% 方法与失败修复，15% 产品进展。避免每篇都写“我又加了一个功能”。公开案例可署名；用户导出作品不强制水印，不以关注/Star 换下载。

## 5. 将“AI 找需求和评论”做成可运营流程

### 输入和搜索

第一阶段采用普通公开检索、明确允许的订阅/投稿入口和用户主动提供的线索。逐来源检查数据使用权限，不默认运行全平台爬虫。搜索摘要只用于发现，参与前必须读原帖与上下文。

首批意图词组，分别组合搜索，不限于某个专用搜索语法：

| 中文意图 | 英文意图 |
| --- | --- |
| AI 架构图 怎么修改 / SVG 改文字 | edit AI-generated SVG / fix SVG text |
| README 缺架构图 / 项目架构可视化 | README architecture diagram / visualize repository architecture |
| RAG 架构图 模板 / Agent 流程图 | RAG architecture diagram template / agent workflow diagram |
| 技术文章 配图 / 好用的画图工具 | diagrams for technical docs / editable technical diagrams |
| 开源项目自荐 / 本周工具推荐 | share your open-source project / submit a developer tool |

中文、英文每天各查看最多 15–20 条新候选；无合适来源时可以少做。高意图问题优先看最近 7 天，策展入口优先看最近 30 天是否仍活跃。较老的明确投稿入口可以保留。

### 资格判断与评分

先过硬条件：原文可核实；具体需要可辨认；JustSVG 当前能解决；参与方式符合当前规则；未拒绝联系；非重复接触。任何一项不满足，进入暂缓或排除，不让评分替代平台许可。

合格线索按 100 分排序：需求明确 30、功能适配 30、可制作有用示例 20、时效 10、参与场景自然 10。每项保留原文依据与理由，不预测私人购买意愿。80 分及以上准备定向回复或投稿；60–79 分用于选题观察；低于 60 分不接触。这是内部排序假设，周复盘后调整。

每条线索记录：URL、语言、平台、公开作者标识、原文日期、发现日期、需求摘要、产品适配、规则来源及检查日期、评分理由、已接触状态、对应案例、文案、发送方式/权限、实际发布链接、反馈与结果。去重以原帖与作者为主，跨平台也避免重复追着同一人推广。

### 内容与发送

优先给具体帮助，再根据上下文说明作者身份和相关资源。没有必要就不带链接；带链接时优先对应图稿/案例，不把所有人引到泛首页。结尾一次只给一个自然动作。

仅作可定制示例，只有实际做完图稿后才能使用“已整理”等描述：

> 你这个场景里，请求链和索引更新链分开画会更容易读。我按你公开的模块说明整理了一张图，SVG 和依据放在案例里。我是 JustSVG 的作者；它可以直接改标签和节点位置。图中的异步部分有一处推断，已经标出来了。

> Separating the request path from the indexing path may make this easier to read. I mapped the modules from your public docs into an editable SVG and marked one inferred relationship. I build JustSVG; the example includes the source and editing steps.

资源投稿骨架：我是作者 → 一句话解决什么 → 针对该读者的具体案例 → 一张图/短演示 → 仓库与演示入口 → beta 与功能边界。未经请求不重复催促；只有对方要求补充、明确投稿流程允许，或有实质新信息时才跟进。

每天最多为中文 2 条、英文 2 条高适配线索准备回复/投稿；这是工作量上限，不是要完成的发送数。无需为了配额降低相关性。没有作者邀请，不去其他项目的 Issue 区投放产品广告；真实文档改进先按其贡献规则沟通，不把 PR 当广告载体。

### 平台执行边界

- **X：** 官方规则禁止仅依据关键词搜索给陌生人自动回复，AI 回复机器人需要事先书面批准，也禁止网页脚本自动化。我可以准备对应案例和文案，但不将 Codex 自动评论列入默认执行。用户若愿意，可自行判断后参与少量真实对话；这不是核心方案依赖。[X 自动化规则](https://help.x.com/en/rules-and-policies/x-automation)
- **Reddit：** 人工和自动的重复、大规模自荐都可能构成垃圾信息；逐社区核对，仅在允许的场景试验。不使用所谓“低于 10% 就安全”的通用比例。[Reddit 官方规则](https://support.reddithelp.com/hc/en-us/articles/360043504051-Spam)
- **HN：** 禁止 AI 生成/编辑的文本和自动发帖。我不代写、润色或代发；用户本人愿意独立写和参与时，才考虑 Show HN。核心计划无需依靠它。[HN Guidelines](https://news.ycombinator.com/newsguidelines.html)
- **Product Hunt：** 后置；可以自行发布，无需购买 hunter，也不能索票。产品可用、已有案例且能回应反馈后再决定。[官方发布指南](https://help.producthunt.com/en/articles/17350772-launch-guide)
- 中文社区发布规则尚未完整核对，因此不承诺批量评论、自动发布或确定的外链权限。平台删除、明确拒绝、警告或限制出现时停止对应动作并查原因。

## 6. 核心内容项目：“给开源项目补一张可编辑的技术图”

这是一条有固定格式、可连续做 3 个月的作品系列。首月制作 6 个案例，每个含中英文说明。前 2 个使用 JustSVG 自身或已验证的通用事件/发布流程，后 4 个优先选择主动征集、明确欢迎文档贡献或已经表达需要的开源项目。

对外部项目查许可证和引用要求，不未经允许重用截图、Logo 和专有素材；依据公开文档自行绘制并标明非官方。没有确认的关系标为推断，外部作者未认可的案例不写成其背书。未征得投稿许可时，可以保留为独立技术研究，不向其 Issue 区强行投递。

每个案例交付：

1. 一张适合信息流查看的预览图。
2. 一份原生 SVG，文字、分组与连线可继续编辑。
3. 中英文技术说明：要回答的问题、阅读顺序、依据、推断和局限。
4. 完整 Prompt、Skill 入口和实际检查记录。
5. 一段 20–40 秒编辑演示；标题时长只是制作规格，不声称完成整个任务只需这么久。
6. 一条中文实践内容、一条英文作品内容、一个适配该案例的投稿包。

首批 6 个选题：

| 案例 | 中文标题方向 | 英文方向 | 证明什么 |
| --- | --- | --- | --- |
| 1 | 给 JustSVG 自己画一张模块架构图 | Mapping JustSVG's architecture | 产品与事实依据都可核验 |
| 2 | 发布流程里的返工和回滚，应该怎么画 | Making rollback paths readable | 有判断、分支与失败处理的真实信息结构 |
| 3 | 一个开源项目的 README，缺的可能是这张图 | One editable diagram for an open-source README | 对维护者的具体价值 |
| 4 | 同一套 RAG 系统，两种阅读方式 | Two ways to explain the same RAG system | 风格服务理解；采用确实需要 RAG 的项目 |
| 5 | AI 图里改一个标签，为什么还要重新生成 | Editing one label without regenerating the diagram | 精确编辑过程；不捏造普遍效率比较 |
| 6 | 从使用者反馈改好一张图 | A diagram revised from real feedback | 有真实互动；尚无反馈时改为失败检查案例 |

另做一份“3 张可复用技术图入门包”：架构、流程、信息图各一张，附 SVG 和 Prompt，放在仓库或发布附件直接下载。无需登录或 Star；这是降低复用门槛的资源，不是诱导互动的赠品。

## 8. 30 天执行安排与验收

| 阶段 | Codex 的具体产出 | 分发动作 | 验收与下一步 |
| --- | --- | --- | --- |
| D1–3 | 基线表、公开入口验收、双语简介与 README 改稿、素材规格、线索表 | 不以发帖凑开局；先确定可访问与可发布的入口 | 两种语言都能找到源码、示例、使用方式和作者 |

持续工作节奏：每个工作批次先读新反馈，再检索/去重、评分、制作案例、准备外发、记录结果；每周只汇报新增信号、有效动作和下一步改变。不在未配置运行机制时宣称会自动每日后台执行；定时运行须在后续执行阶段单独设置。

## 9. 指标、归因与停止条件

首月暂定目标，D1 建立实际基线后确认：新增 **100 个仓库 Star、10 个个人 GitHub 关注、3 次独立公开分享、5 个可核验的外部复用案例**。它们是用于判断实验的目标，不是保证，也不能把 AI 自产案例算作外部复用。个人 X 关注、中文账号关注分开记录，不跨平台直接相加当成独立人数。

两种语言分开记录内容、投稿、相关回复与可观察来源访问；Star、GitHub 个人关注报告总量。无法判断语言来源时保留“未知”，不硬分摊。

| 层级 | 记录方式 | 用途 |
| --- | --- | --- |
| 投入 | 每份案例、检索、投稿、参与的耗时与工具开销 | 计算每个有效信号的投入 |
| 分发 | 实际发布/投稿链接，采纳、相关回复、独立分享 | 区分“发了很多”和“有人响应” |
| 承接 | 可获得的汇总访问、仓库访问、图稿/附件下载 | 判断读者是否进一步了解 |
| 传播 | Star 净增、个人 GitHub 关注净增、外部引用/复用链接 | 对应本阶段目标 |

UTM/来源标识不能直接证明某个人因某条评论而 Star。归因使用渠道可提供的汇总访问、发布前后变化和用户自愿反馈；将相关性写成相关性。数据不足就保留未知，不据小样本算“精准获客率”。

预设调整规则：

- 某类线索完成 10 次合格参与但没有相关回复、可观察的后续访问或复用信号：暂停该类，检查受众、例图和文案。10 次只是早期诊断门槛，不是统计结论。
- 有相关回复但不访问仓库：先改链接对应关系和价值说明。
- 有访问但没人进一步体验或关注：用至少 3 个直接反馈排查首屏、语言和功能适配；不先加评论量。
- 只有 Star，没有复用：继续保留传播成果，但下轮改用更贴近实际任务的案例，不据此宣布产品需求已验证。
- 策展未回复：不靠持续催促提高“完成量”；补案例或换适配目标。
- 平台删除、拒绝、警告或限制：暂停该平台对应动作，不用换号或改写规避。

首月结果较弱时，分别保留中文与英文至少一条验证路径；在“中英文同等投入”要求改变前，不因一侧短期爆款而把另一侧预算挪走。

## 10. 执行分工和开始条件

后续明确启动后，Codex 可承担产品与入口检查、线索研究、去重评分、图稿和录屏制作、双语案例、README/文档修改、投稿准备、通过可用且许可的方式执行已授权的发布/投稿，以及记录复盘。公开作者叙事以用户真实经历和认可的判断为依据。

用户必须处理的事项控制在账号归属、登录/验证码、真实个人经历与身份确认、必要的第三方平台权限。需要本人参与的平台单独选择；尤其 X 主动评论不能默认全自动，HN 必须本人独立写作。若用户不愿手工参与，核心方案仍可围绕 GitHub、作品包与允许的策展投稿运行。

当前可用工具未建立 X、掘金或邮件发布连接。因此“以后可以执行”需要在启动时落实具体通道，不能把文案准备记成已发布。没有可用通道时交付可审阅发布包并转向能完成的渠道；不绕过验证或伪造发送结果。

启动所需信息：确认公开仓库与演示 URL、使用的个人昵称与账号、允许发布/投稿的渠道和批次范围、可接受的实际费用上限。先交付完整可审阅的首批案例与外发材料；后续授权按清晰批次执行，不要求用户逐句运营。此方案没有创建定时任务或进行任何外发。
